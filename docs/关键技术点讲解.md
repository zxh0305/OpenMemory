# 混合检索（Hybrid Search）

## 当单一搜索不够用时

---

### 问题：用户搜一个东西，三种搜索方式各有什么盲区？

先看一个场景。用户的记忆库里有一条：

> "我上个月在望京 SOHO 跟张经理签了合同，每月物业费 3200。"

现在 Claude 问："张经理的合同物业费是多少？"

| 搜索方式 | 能不能找到？ | 为什么 |
|---------|------------|--------|
| **语义搜索**（Qdrant 向量） | ⚠️ 可能找到 | "物业费"语义相似，但"张经理"这个专有名词向量化后位置不稳定 |
| **关键词搜索**（ILIKE/FTS BM25） | ✅ 精确命中 | "物业费"直接匹配，但不知道"每月费用"也是物业费 |
| **实体匹配**（MemoryEntity） | ✅ 精确命中 | "张经理"作为实体精确命中 |

**结论：单一搜索方式各有盲区，组合起来才是正解。**

---

### 方案：三路信号 + RRF 融合

```
用户输入 query "物业费"
         │
         ├──────────────────────────────────────────────┐
         │                      │                       │
         ▼                      ▼                       ▼
  ┌─────────────┐      ┌──────────────┐      ┌──────────────┐
  │  Qdrant 向量 │      │  FTS5 BM25   │      │ MemoryEntity │
  │  语义搜索    │      │  关键词搜索   │      │  实体索引     │
  │             │      │              │      │              │
  │ embedding → │      │ 分词 → term  │      │ 精确匹配     │
  │ 向量相似度   │      │ → BM25 分数  │      │ → entity hit │
  └──────┬──────┘      └──────┬───────┘      └──────┬───────┘
         │                      │                       │
         │          rank₁ = 3   │     rank₂ = 1         │    rank₃ = 5
         └──────────────────────┴───────────────────────┘
                                      │
                                      ▼
                        ┌─────────────────────────┐
                        │    RRF 融合              │
                        │                          │
                        │  score = Σ 1/(k + rank)  │
                        │  k = 60                  │
                        │                          │
                        │  1/(60+3) + 1/(60+1)     │
                        │  + 1/(60+5) = 0.048      │
                        └──────────┬──────────────┘
                                      │
                                      ▼
                         最终排序 → 返回结果

```

---

### 为什么用 RRF 而不是加权平均？

最简单直觉的方案是加权平均：

```
score = w₁ × 向量分 + w₂ × BM25分 + w₃ × 实体分
```

但这条路走不通，原因：

| 问题 | 说明 |
|------|------|
| **量纲不同** | 向量距离在 0~1 之间，BM25 分数可能到 10+，实体命中只有 0/1 |
| **权重难调** | w₁/w₂/w₃ 需要大量标注数据做超参搜索 |
| **场景不鲁棒** | 数据分布变了，之前的权重就失效 |

**RRF 绕过了所有问题**——它不看分数绝对值，只看**相对排位**。

```
RRF score = Σ 1/(k + rank_i)
```

- rank_i 是第 i 路信号中这条结果的排名（第 1 名 → rank=1）
- k 是平滑常数（本项目 k=60），防止 rank 很小的结果分数过大
- 结果**在每路信号中都排得靠前** → RRF 分数高

**直观理解：**
> 每条记忆在三场选举中分别投票，你在三场都得票靠前你就赢，某一场得票极高但其他场没票也不行。

---

### 兜底降级：挂了一路怎么办？

```python
def hybrid_search(query, user_id, limit, memory_client):
    results = []

    # 信号 1：向量搜索
    try:
        vector_results = search_qdrant(query, memory_client)
    except Exception:
        vector_results = []   # Qdrant 挂了 → 空结果，不崩

    # 信号 2：BM25
    try:
        bm25_results = search_bm25(query)
    except Exception:
        bm25_results = []

    # 信号 3：实体匹配
    try:
        entity_results = search_entities(query)
    except Exception:
        entity_results = []

    # 仅用可用信号做 RRF
    return rrf_merge(vector_results, bm25_results, entity_results)
```

**效果：Qdrant 挂了 → 降级为 FTS5 + 实体检索，功能不完全中断。**

# source_raw_input_id

## 一个外键的设计取舍

---

### 场景：记忆和原始输入的关联

系统里有两条记录：

| 表 | 内容 |
|----|------|
| `raw_memory_inputs` | 用户原始输入："我喜欢喝冰美式，每天早上都喝" |
| `memories` | AI 提取后的事实："用户喜欢喝冰美式" |

两条记录之间存在关联。关联怎么表示？

---

### 改前方案：JSON 里藏 ID

```python
# memories.metadata_ 是一个 JSON 字段
memory.metadata_ = {
    "raw_record_id": "3d996e88071a4e9ba717a31313b94d22",
    "fact_index": 1,
    ...
}
```

查关联记忆时：

```python
# 需要全表扫描 + 字符串匹配
candidate_memories = db.query(Memory).filter(
    Memory.user_id == raw_input.user_id,
    Memory.app_id == raw_input.app_id,
).all()

for memory in candidate_memories:
    if memory.metadata_.get("raw_record_id") == str(raw_input.id):
        # 找到了 ← 这里只是字符串相等判断，没有索引可走
```

**问题：**

| 问题 | 严重程度 |
|------|---------|
| 无法建外键约束 | JSON 字段不支持 ForeignKey |
| 全表扫描 | 没有索引，O(n) 复杂度 |
| JSON 解析开销 | 每次读取 metadata_ 需要反序列化 |
| 无法级联操作 | 删 RawMemoryInput 不会自动删关联 Memory |

**一句话：metadata 存 ID 是 NoSQL 思维，放在关系型数据库里就是用错了工具。**

---

### 改后方案：显式外键

```python
class Memory(Base):
    __tablename__ = "memories"
    ...
    # 新增：显式外键
    source_raw_input_id = Column(
        String(32),
        ForeignKey("raw_memory_inputs.id"),
        nullable=True,   # 旧数据没有，允许 NULL
        index=True       # 加索引，查询 O(1)
    )
    raw_input = relationship(
        "RawMemoryInput",
        back_populates="memories"
    )

class RawMemoryInput(Base):
    __tablename__ = "raw_memory_inputs"
    ...
    memories = relationship(
        "Memory",
        back_populates="raw_input"
    )
```

查关联记忆变成：

```python
# O(1)：直接通过外键 + 索引查询
raw_input.memories

# 等同于 SQL
# SELECT * FROM memories WHERE source_raw_input_id = 'xxx'
```

---

### 关键设计决策：为什么允许 NULL？

```python
source_raw_input_id = Column(
    String(32),
    ForeignKey("raw_memory_inputs.id"),
    nullable=True,    ← 重要
    index=True
)
```

**不允许 NOT NULL 的原因：**

1. **现有数据没有这个值** — 线上已有几万条记忆没有 `source_raw_input_id`，加 NOT NULL 会导致迁移失败
2. **向后兼容** — 旧代码路径可能没有设置这个字段，NULL 意味着"未关联"

**妥协方案：**

```python
# 查询时同时处理新旧数据
linked_memories = []

# 新数据：FK 查询（O(1)）
fk_memories = db.query(Memory).filter(
    Memory.source_raw_input_id == raw_input.id
).all()
linked_memories.extend(fk_memories)

# 旧数据：metadata 回退（O(n)，仅对 NULL 的记录）
old_records = db.query(Memory).filter(
    Memory.source_raw_input_id == None,
    Memory.user_id == raw_input.user_id,
).all()
for mem in old_records:
    if mem.metadata_.get("raw_record_id") == str(raw_input.id):
        linked_memories.append(mem)
```

> **新数据走 FK 快路径，旧数据走 metadata 慢路径。随着时间推移，旧数据越来越少，慢路径最终消失。**

---

### 收益对比

| 维度 | 改前（JSON metadata） | 改后（FK + relationship） |
|------|---------------------|------------------------|
| 查询复杂度 | O(n) 全表扫描 + JSON 解析 | O(1) 索引查找 |
| 引用完整性 | 无约束 | ForeignKey 保证 |
| 级联能力 | 手动写逻辑 | 数据库级联（可配置） |
| ORM 友好度 | 手动字符串比较 | `raw_input.memories` 直接取值 |
| 旧数据兼容 | — | NULL 回退到 metadata |

# FTS5 全文索引

## 同样的查询，三个数量级的差距

---

### 问题：查一条记忆，数据库在做什么？

```sql
SELECT * FROM memories WHERE content LIKE '%物业费%';
```

这条 SQL 在数据库内部的执行过程：

```
memories 表（假设 10 万行）
         │
         ▼
  ┌─────────────────────────────┐
  │  SCAN 全表扫描               │
  │                              │
  │  row 1:  "我喜欢喝冰美式"    │ ← LIKE '%物业费%'? → NO
  │  row 2:  "用户住北京"        │ → NO
  │  row 3:  "每月物业费3200"    │ → YES ✓
  │  row 4:  ...                │
  │  ...                        │
  │  row 100000: ...            │
  └─────────────────────────────┘
```

**没有索引，引擎就只能把每一行读出来，逐条检查。**

| 数据量 | 耗时 |
|-------|------|
| 1,000 条 | ~50ms |
| 10,000 条 | ~500ms |
| 100,000 条 | ~5s |

**每多 10 倍数据，慢 10 倍。**

---

### FTS5 的解法：倒排索引

FTS5 做的事：**提前建好词典，查词典而不是查数据。**

建索引的过程：

```
原始数据：
  row 1: "我喜欢喝冰美式"
  row 2: "用户住北京"
  row 3: "每月物业费3200元"

分词器切词后，建立倒排索引：

┌──────────┬────────────┐
│  term    │  doc IDs   │
├──────────┼────────────┤
│ 喜欢     │  1         │
│ 冰美式   │  1         │
│ 用户     │  2         │
│ 住       │  2         │
│ 北京     │  2         │
│ 每月     │  3         │
│ 物业费   │  3         │  ← "物业费" 出现在 row 3
│ 3200元   │  3         │
│ ...      │ ...        │
└──────────┴────────────┘
```

搜索时：

```sql
SELECT * FROM memories_fts WHERE content MATCH '物业费';
```

```
1. 查词典：term = "物业费" → doc IDs = [3]
2. BM25 计算相关性分数
3. 返回排序后的结果  ← 不需要扫描全部数据！
```

**时间复杂度从 O(n) 降到 O(1)——只查词典命中条目，不查不相关数据。**

---

### BM25 排序：不只是"有没有"，还要"多相关"

FTS5 不只是返回匹配结果，还给每个结果算一个**相关性分数**：

```
BM25(d, q) = Σ IDF(t) × TF(t, d) × (k₁ + 1) / (TF + k₁ × (1 - b + b × |d|/avgdl))
```

不需要记公式，理解它的**直觉**：

| 因素 | 对分数的影响 | 直观理解 |
|------|------------|---------|
| **词频 TF** | 词出现越多次，分数越高 | 提了 3 次"物业费"比提 1 次更相关 |
| **逆文档频率 IDF** | 稀有词权重更高 | "物业费"比"的"更有区分度 |
| **文档长度归一化** | 短文档中匹配到更珍贵 | 10 个字的标题里出现比 1000 字文章里更有价值 |

**对比 ILIKE**

```
LIKE '%物业费%':
  "每月物业费3200元"        → 命中（无法排序）
  "物业费物业费物业费物业费"  → 命中（仍然无法排序）
  两条结果分不出谁更相关

FTS5 BM25:
  "每月物业费3200元"        → BM25 分数：3.2
  "物业费物业费物业费物业费"  → BM25 分数：8.7（词频更高）
  两条分数不同，可以按相关性排序
```

---

### 同步策略：对业务代码零侵入

FTS 索引和业务数据的同步是一个经典问题。这里采用**事件驱动同步**：

```
创建记忆
    │
    ▼
  ┌─────────────────────┐
  │  SQLAlchemy          │
  │  after_insert 事件   │  ← 自动触发，对业务代码透明
  │                      │
  │  sync_memory_to_fts()│
  │  → INSERT/REPLACE    │
  │  → FTS5 虚拟表       │
  └─────────────────────┘
```

```python
# 通知式同步：创建记忆后自动写 FTS
create_memory_record(...):
    memory = Memory(...)
    db.add(memory)
    db.commit()

    # 业务代码不需要知道 FTS 的存在
    sync_memory_to_fts(memory.id, content)
```

```python
# 多个写入点统一处理
# 路径 1：REST API 创建 → sync_memory_to_fts()
# 路径 2：MCP add_memories → sync_memory_to_fts()
# 路径 3：更新记忆 → sync_memory_to_fts()
# 任何路径漏掉 → FTS 数据不一致
```

**这里有个问题：三个写入路径都要手动调用 `sync_memory_to_fts()`。一个更好的方式是用 SQLAlchemy 的 after_insert 事件统一处理，但目前是手动调用。这是后续可以改进的点。**

### 性能对比

```
数据量 10 万条，搜索 "物业费"

┌──────────┬──────────────┬──────────────┐
│          │   ILIKE       │   FTS5       │
├──────────┼──────────────┼──────────────┤
│ 耗时     │  ~5000ms     │  <10ms       │
│ 排序     │  无           │  BM25 排序   │
│ 索引结构  │  无           │  倒排索引    │
│ 中文分词  │  不支持       │  支持        │
│ 资源消耗  │  CPU 100%    │  <1%         │
└──────────┴──────────────┴──────────────┘

5000ms vs 10ms = 500 倍差异
```

---

### 一句话总结三页内容

> **混合检索用 RRF 融合向量 + 关键词 + 实体，解决单一搜索盲区；**
> **source_raw_input_id 用外键替代 JSON 字段，让关联查询从 O(n) 降到 O(1)；**
> **FTS5 用倒排索引替代全表扫描，同样的查询快 500 倍。**
