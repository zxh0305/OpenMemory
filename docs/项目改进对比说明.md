## 每项改动详情

### 1. source_raw_input_id 外键

**文件：** `api/app/models.py`、`api/app/schemas.py`、`api/app/routers/memories.py`

**改了什么：**
```python
# Memory 表增加外键列
source_raw_input_id = Column(
    String(32),
    ForeignKey("raw_memory_inputs.id"),
    nullable=True, index=True
)
raw_input = relationship("RawMemoryInput", back_populates="memories")

# RawMemoryInput 增加反向关系
memories = relationship("Memory", back_populates="raw_input")

# 创建记忆时自动绑定
memory = Memory(..., source_raw_input_id=raw_input.id)
```

**为什么改：**
之前 Memory 和 RawMemoryInput 的关联依赖 `metadata_.raw_record_id` 字符串匹配。这是 JSON 字段里的一个 key，不是外键约束——没有引用完整性，查询时需要遍历所有候选记忆做字符串比较，复杂度 O(n)。

**测试效果：**
```
# 创建记忆后查看详情
curl /api/v1/memories/{memory_id}
→ "source_raw_input_id": "3d996e88071a4e9ba717a31313b94d22"
→ "source_raw_input": {
    "original_text": "我喜欢喝冰美式",
    "extracted_facts": ["用户喜欢喝冰美式"],
    "processing_status": "stored_without_ai"
  }

# 原始输入详情改为 FK 查询
curl /api/v1/memories/raw-inputs/{id}
→ linked_memories: 1 条（通过 source_raw_input_id 直接 JOIN）
  验证：之前用 metadata 字符串匹配，现在用外键直接关联
  数据库确认：SELECT COUNT(*) FROM memories WHERE source_raw_input_id IS NOT NULL
```

### 2. Route 顺序修复

**文件：** `api/app/routers/archived_memories.py`

**改了什么：**
`/stats/summary` 路由从 `/{memory_id}` 后面移到前面。

**为什么改：**
防御性修改。FastAPI 的路由按注册顺序匹配，虽然 `{memory_id}`（`str` 类型）不会匹配 `/stats/summary`（多段路径），但后续如果修改路径参数类型或增加新路由，容易被动态路径吞掉。让静态路径排在动态路径前面是标准做法。

**测试效果：**
```bash
curl "http://localhost:8765/api/v1/archived-memories/stats/summary?user_id=demo"
# 返回: {"success":true,"total_archived":0,...}
# 证明路由正确命中 GET /stats/summary handler，没有被 /{memory_id} 拦截
```

### 3. Metadata 键名统一

**文件：** `api/app/routers/archived_memories.py`

**改了什么：**
```python
# 改前
"metadata": archived_memory.metadata_,

# 改后
"metadata_": archived_memory.metadata_,
```

**为什么改：**
所有 Memory 接口返回 `metadata_`，但 `ArchivedMemory` 详情接口返回 `metadata`。前端需要写两套解析逻辑。

**测试效果：**
```bash
curl /api/v1/archived-memories/{id}?user_id=demo
# 改前: {"metadata": {...}}
# 改后: {"metadata_": {...}} → 与 /api/v1/memories/{id} 一致
```

### 4. Archive API 改用 Pydantic Body

**文件：** `api/app/routers/memories.py`

**改了什么：**
```python
# 改前：query params
@router.post("/actions/archive")
async def archive_memories(
    memory_ids: List[UUID],
    user_id: UUID,
    db: Session = Depends(get_db)
):

# 改后：Pydantic body
class ArchiveMemoriesRequest(BaseModel):
    memory_ids: List[UUID]
    user_id: str

@router.post("/actions/archive")
async def archive_memories(
    request: ArchiveMemoriesRequest,
    db: Session = Depends(get_db)
):
```

**为什么改：**
create_memory、pause_memories、delete_memories 都用 JSON body，唯独 archive 用 query params。OpenAPI 文档不一致，部分客户端自动生成的代码无法正常工作。

**测试效果：**
```bash
curl -X POST "http://localhost:8765/api/v1/memories/actions/archive" \
  -H "Content-Type: application/json" \
  -d '{"memory_ids": ["xxx"], "user_id": "demo"}'
# → 404 {"detail": "Memory not found"}（进入正确 handler，body 正确解析）
```

### 5. MCP 搜索结果增加字段

**文件：** `api/app/mcp_server.py`

**改了什么：**
```python
# 改前
memories.append({
    "id": ..., "memory": ..., "score": ...,
    "created_at": ..., "updated_at": ...
})

# 改后
memories.append({
    "id": ..., "memory": ..., "score": ...,
    "created_at": ..., "updated_at": ...,
    "app_name": memory_obj.app.name,        # 来源应用
    "source": "hybrid_search",               # 搜索方式
    "decay_score": memory_obj.decay_score,           # 衰退分数
    "importance_score": memory_obj.importance_score,  # 重要性
})
```

**为什么改：**
Claude 搜索记忆后看不到记忆来自哪个应用（微信/对话/笔记），也看不到失效程度。有了 app_name 可以判断上下文，有了 decay_score 可以判断是否过时。

**测试效果：**
```python

# 改前：{"id": "xxx", "memory": "用户住北京", "score": 0.8}
# 改后：{"id": "xxx", "memory": "用户住北京", "score": 0.8,
#        "app_name": "wechat", "source": "hybrid_search",
#        "decay_score": 0.95, "importance_score": 0.7}
# Claude 可以判断：来自微信、几乎未衰退、可信度较高
```

### 7. 混合检索

**文件：** `api/app/utils/search.py`（**新增**，222 行）

**改了什么：**
新增三路信号融合搜索：
```
输入 query
  ├─→ Qdrant 向量搜索（语义相似度）
  ├─→ FTS5 BM25（关键词相关度）
  └─→ 实体索引（精确匹配）
       ↓
  Reciprocal Rank Fusion (RRF, k=60)
       ↓
  最终排序结果
```

**为什么改：**
单一搜索方式有盲区：纯语义搜索对专有名词召回差，纯关键词无语义泛化。三路融合后互补短板。REST 和 MCP 搜索接口统一调用，结果可对比。

**测试效果：**
```bash
curl -X POST /api/v1/memories/filter \
  -d '{"user_id": "test", "search_query": "电费"}'
# 内部调用 hybrid_search → 向量 + BM25 + 实体 → RRF 融合排序
```

### 8. 实体提取与索引

**文件：** `api/app/utils/entity_index.py`（**新增**，222 行）

**改了什么：**
```python
# 新增 MemoryEntity 表
class MemoryEntity(Base):
    memory_id → ForeignKey(memories.id)
    entity_text → "张三"
    entity_type → "person"

# 创建记忆时自动提取实体
extract_entities_from_facts(facts) → [{"text":"张三","type":"person"}]
save_entities_for_memory(memory_id, entities)
```

**为什么改：**
专有名词（人名/地名/产品名）在向量空间中的位置不确定，纯语义搜索可能漏掉。实体索引提供精确匹配，混合检索时提升专有名词的召回率。

**测试效果：**
```
创建记忆 "张三住在北京" → 自动提取 "张三"(person) + "北京"(location)
→ 搜索 "张三" → 实体索引精确命中 → 排名提升
```
